Class diagram per domain

The same model split into bounded contexts: one context = one microservice = one database. Inside a domain, associations are real JPA relationships. Between two domains, only an identifier is kept.

Between two domains

RuleIn JobBoard
A domain stores only the id of an object owned by another domainCandidature stores candidateId and jobId (plain Long values, no @ManyToOne)
One database per service, no foreign key between servicescandidat_db, job_db, candidature_db, meeting_db, notification_db
Data from another domain is read through its APIGET /api/candidates/{id} and GET /api/jobs/{id} with OpenFeign
… or received in an eventmeeting and notification get the ids in ApplicationSubmitted

The candidature classes

  • Candidature: the JPA entity, with candidateId and jobId.
  • CandidatureResponse: the record returned to the client (application + candidate + job read through Feign).
  • ApplicationSubmitted: the event published to RabbitMQ after the INSERT.

Microservice numbering

  • MS1 candidat · MS2 job · MS3 candidature
  • MS4 meeting (Node.js) · MS5 notification (Python)
  • RabbitMQ, Eureka, Config Server, Keycloak and the gateway are infrastructure, not microservices.
